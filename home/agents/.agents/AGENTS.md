# Global preferences

## Choices

- Pronouns: he/him.
- Keep system behavior close to distro/upstream defaults.
- I use fish, Firefox, and nvim. Python is uv (`uv sync`, `uv run`), never pip or a hand-activated venv.
- My GPU is a 6 GB RTX 4050 Laptop. When a job doesn't fit it (VRAM, OOM, hours of GPU), point once at molab (molab.marimo.io: a free 96 GB RTX PRO 6000 per notebook, 12 h sessions, unlisted but public, so no sensitive data); don't bring it up otherwise.
- Dataframes: polars, not pandas; convert where a library hands back pandas.
- Python line length is PEP 8: 79 for code, 72 for comments and docstrings. Lint it (ruff `E501`, `W505` with `max-doc-length = 72`). Never run `ruff check --select RUF100 --fix` (it removes `# noqa` markers for unselected rules); use `--extend-select RUF100` on the project config.
- Prose is not hard-wrapped: a paragraph in a markdown cell, README, doc, or note is one line, and a list item is one line.
- Markdownlint config lives per project (`.markdownlint.yaml` at the project root); do not add a `$HOME` config or pin `--config` in nvim/conform.

## Working

- Global agent instructions (`~/.agents/AGENTS.md`, `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, `~/.gemini/config/AGENTS.md`) and skills (`~/.agents/skills/`) are stow symlinks; edit their targets under `~/dotfiles/home/agents/.agents/` (a skill's real folder is `~/dotfiles/home/agents/skills/<name>/`; the links are dir symlinks because Codex ignores a symlinked `SKILL.md`).
- If `~/.agents/AGENTS.local.md` exists, read it for machine-local/private context not tracked in the public dotfiles repo.
- Read files, logs, and command output yourself; don't ask me to paste them. Make config changes by writing files, not GUI walkthroughs.
- When I say something confuses me, don't rewrite it on a guess: ask me in small parts (a sentence, a term, a step at a time) what exactly is unclear until the cause is pinned down, then fix that.
- Don't build a fix for a cause you haven't proven. Add logging that pins it down first, then fix what it shows. Never change a setting I chose (a resolution, frame rate, size) to chase a symptom. When a config edit answers my request, make it and stop; if it doesn't take effect where I'm looking, say why (stale process, a rule that applies only on map) instead of writing code around it.
- Writing that goes out under my name (mail, messages, PR text, posts, and issues for repos that aren't mine): read `~/projects/writing/AGENTS.md` (or `CLAUDE.md`) and `STYLE.md` first and work in that repo, not `/tmp`. An issue in my own repo (`github.com/jaehho/`) needs no draft: file it directly.
- When interacting with Cloudflare, use the `cf` CLI unless the project has a Wrangler configuration file.
- Google services (Gmail, Calendar, Drive, Docs) go through the `gog` CLI; `gog auth list` shows the accounts, `gog --help` the commands. Pass `--readonly` unless I ask for a change, and never send mail without asking.
- `!` commands have no TTY, so anything that prompts (sudo, `ssh -t`, pickers) needs a separate terminal.
- Stop a process by the PID you recorded at start or by exact name (`pkill -x`), never `pkill -f` or `pgrep -f | xargs kill`: the pattern matches shell wrappers and my real instance started with the same arguments. To find a lost PID, use the port (`ss -ltnp`) or a self-excluding pattern (`pgrep -f '[n]ame'`), then `kill` it.
- Never `source` a secrets file (a `.env`, `~/.config/*.env`) in a command: a failed source prints its tokens into the session.
- Unfamiliar or possibly-new names are lookup prompts, not inference prompts; assume anything may postdate training data. Check docs or source before asserting, and say what remains unverified. This includes the defaults and behavior of tools I already know (a linter's default rule set, a flag's default): read the docs or run the tool's own CLI, not memory. For cited works, check Zotero before web search.
- Library docs, in this order: the installed source and `--help`; the clones in `~/projects/upstream` (`git -C <dir> describe --tags --always` gives a clone's version); context7, whose docs can be newer than the installed version. If a library whose prose docs you need is missing and its source is in a git repo, shallow-clone it at the installed version's tag into `~/projects/upstream` and say what you cloned.
- Exercise the path I will hear, see, or click, or say which narrower thing you checked.
- To test or screenshot a GUI, web page or browser app, load the `gui-testing` skill first. **Never take my focus or keyboard**: the Playwright MCP browser is meant to open on a silent `playwright` workspace (`hyprland.lua`); if a window ever takes focus, stop using it and tell me.
- In long sweeps, decide as I would, minimize intervention (ask only when truly blocked), and use isolated proxies (scratch tmux, pty, headless browsers) rather than nested compositors or live windows.
- Before running a sync, reconcile, or apply script, read all of its dry-run output and apply only the changes I asked for. For declarative sync/reconcile tools, keep destructive cleanup of undeclared state out of unattended converge and behind a separate manual command with `--dry-run`.
- If a permission classifier or sandbox blocks `makepkg` on AUR packages, clone and review the PKGBUILD, stage edits in scratch, and put `makepkg --nodeps` at the top of the user-run `/tmp/` script.

## Projects

- Add a test when a rule breaks silently and is cheap to check (network boundaries, path literals, imported helpers). Don't test style, prose, or section conventions; research needs room to move.
- When a change touches several similar things (notebooks, modules, the same bug in several places), make it in one instance first and wait for confirmation before rolling it out to the rest.
- Commit work in small commits instead of leaving it uncommitted. A task's first commit takes its real type (`fix(scope):`); only follow-up commits are `wip(scope):`. Never discard uncommitted work (`git checkout`/`restore` on a file). Before you edit a file that holds my uncommitted changes (review comments included), commit mine alone first, so the record shows what I wrote.
- Work in the current checkout, on the branch that is checked out, and create a branch only as this rule calls for. A worktree of your own is for testing or work that could disturb mine; when it is safe, merge the result into the current checkout and remove the worktree before handing back. In a worktree, unset `VIRTUAL_ENV` and `UV_PROJECT_ENVIRONMENT` before running uv, or it syncs the main checkout's `.venv`. A task (a feature, bug fix, or experiment) that needs a second commit gets a topic branch: move the first commit onto it, and reset the default branch only if that commit is unpushed. Merge when the task is complete to my satisfaction: if it looks done, say it is ready to merge and wait for my confirmation — silence is not yes. On confirm, merge with `--no-ff` and a real message, so `git diff M^1 M` is the net change, then delete the topic branch.
- Tasks, gotchas, and design decisions live in GitHub issues, never in TODO.md, ISSUES.md, or DESIGN_LOG.md. Label gotchas `gotcha` (symptom, evidence, recovery, verification; open until believed fixed, reopen on recurrence) and decisions `decision` (what and why; closed once decided). Before changing broken behavior, search both labels open and closed. When writing `gh issue create`/`comment` bodies, use a quoted heredoc or `--body-file` with plain backticks (never backslash-escaped backticks).
- Root docs, each only when it has content: `README.md` (install, use, what it is and how it works), `CHANGELOG.md` (release notes, for published packages), `AGENTS.md` (and `CLAUDE.md` symlink where needed, agent rules and pointers only). Projects with a UI that the impeccable skill works on also keep `PRODUCT.md` and `DESIGN.md`, which it reads by name.
- Meetings steno recorded about a project are in its `notes/meetings/` (generated, read-only; start at `README.md` there).
- My apps run live from their checkouts: `make install` writes launchers under `~/.local` (no sudo, no `/usr` package), so a merge ships by rerunning it or relaunching. Their `packaging/PKGBUILD` feeds the AUR; never install it here (dotfiles #67). Their names, the links between them, background running and dev safety follow `~/dotfiles/docs/app-contract.md`. An app's `.venv` is production: read a value with `grep` or `.venv/bin/python -I`, never `uv run`/`uv sync` in its checkout, which can rebuild the venv (steno#41).
- Before handing an app to me to test, quit my running copy (if it is recording or syncing, wait and say so) and start the build under test through the compositor (`hyprctl eval "hl.exec_cmd('env <NAME>_SRC=<tree> ~/.local/bin/<name>')"`), so its window is open when you report. Never hand me launch commands. After my verdict, put the normal copy back unless the merge made it current.
- Writing agent files, rules, skills, or READMEs: read `~/dotfiles/docs/writing-claude-files.md` (sources and dated checks).
- Before an upstream issue or PR: read `CONTRIBUTING.md`, the templates, and the org's policies in its `.github` repo, and follow them. An AI-usage policy can ban AI-written text: hyprwm (Hyprland, hypr*) does, and auto-closes PRs from unvouched accounts, mine included; there, give me the evidence and I write the text. Then search open and closed issues and PRs; comment on an existing thread rather than filing. Find who writes the good ones (list issues by label through the tracker API, count authors, compare median description length), read three to five of the same kind, and match their title style, structure, and length. Put long evidence in your own issue or an attachment, not the report; keep the prose simple and add detail only when the repro needs it. Open PRs as drafts unless I say otherwise.
- A repo that isn't only mine keeps its own conventions: one where `git shortlog -sne HEAD | head -5` lists an author besides me (the repo's `user.email` or `jaehho`'s GitHub noreply address; `[bot]` authors don't count), or whose `origin` is outside `github.com/jaehho/`. There, drop these rules: committing unasked and `wip` commits, topic branches and merges, filing tasks as issues with `gotcha`/`decision` labels, the root-docs set, polars, and the 79/72 line length. Instead, commit only when I ask; ask before a push, an issue or a comment; follow its dataframe library, line length, lint settings and packaging files; fix only lint on lines you change or that your change causes; and still use uv locally (`uv venv`, `uv pip install -r`, `uv run --with`). The other rules hold there too, including never discarding uncommitted work, one instance first, and the upstream issue and PR rule.

## Skills, Hooks, and Memory

- Auto-memory is project-local. Before saving a memory for a correction, find the `AGENTS.md` / `CLAUDE.md`, rule, or skill that caused the behaviour and fix it there; save a memory only when no file owns the rule.
