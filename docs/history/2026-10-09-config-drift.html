Config drift

What the repo owns, what is actually on this machine, how those two can come apart, and what puts them back. Inventoried on the laptop, 2026-10-09. Right now nothing has drifted; the cards below are the modes that can.

Right now 25 stow packages linked 10 system links 6 copies + 3 NM dispatchers synced 0 .pacnew packages in sync

Three layers, three live forms

The repo is always the source of truth. The live form is what a running process actually reads. Those are not the same kind of object, so they drift differently.

Stow
home/<pkg>/…  →  ~/…   e.g. ~/.config/hypr/hyprland.lua
symlinkper file
System links
system/…  →  /etc/…   e.g. /etc/keyd/default.conf
symlinkruntime readers
System copies
system/…  →  /etc/…   e.g. /etc/default/grub
real root fileboot / sandbox / PAM

Why copies exist. Some readers cannot follow a link into /home: systemd-logind (ProtectHome=yes), udev (private mounts, also runs from initramfs), PAM (login must work with a broken /home), grub/mkinitcpio (before /home is mounted), reflector (ProtectHome=true). NetworkManager dispatcher scripts are copies too: NM refuses a symlink or a non-root script.

Stow: home/* → ~/

Once a package is stowed, each file is a relative symlink into the repo. Editing the repo file is editing the live file. Drift is about structure (new, deleted, or overwritten links), not content.

Edit a linked file

You change home/fish/.config/fish/config.fish. The live file is the same inode path via symlink.

Drift: none. Already live.

Fix: nothing.

Add a new file to a package

You create home/fish/.config/fish/conf.d/foo.fish. Nothing puts it in ~/.config/fish/conf.d/ until stow runs.

Drift: live tree missing a file. Invisible to the program.

Fix: stow / dotfiles apply.

Delete a file from the repo

The symlink in ~ stays behind and now dangles. Nothing unlinks it: the stow step only walks files still in the package.

Drift: orphan link. Some tools error on a dangling path.

Fix: remove the orphan by hand, or restow after a cleanup pass. Today converge does not catch this.

Something writes a real file over a link

A GUI or installer replaces ~/.config/kitty/kitty.conf with a regular file. The repo is now ignored for that path.

Drift: two sources of truth. Edits to the repo do nothing.

Fix: apply backs the real file up to *.bak and recreates the symlink. The .bak is the discarded live copy.

New package in the repo

You add home/foo/. Until stow runs it is not in the live tree at all.

Drift: whole package absent.

Fix: dotfiles apply.

Generated files (not drift)

mimeapps.list and waypaper's config.ini are written at runtime by other processes. The repo holds a seed, not the source of truth.

Fix: nothing, by design. They are skipped on purpose.

System links: system/ → /etc

Same as stow: the live path is a symlink into the repo, so content cannot drift. Structure can.

Edit a linked system file

Change system/keyd/default.conf. keyd reads /etc/keyd/default.conf, which is the link.

Drift: none in the file. A running service may still hold the old bytes until restart (keyd, sysctl).

Fix: reload the service. Converge does this when the file hash changes.

Link missing or replaced

A package or a hand command replaces /etc/sysctl.d/99-sysrq.conf with a regular file, or the link is never made on a new machine.

Drift: repo change no longer reaches the live path.

Fix: apply relinks with ln -sfn.

System copies: system/ ⇉ /etc

This is the only layer where content can drift. The live file is a real root-owned copy. The repo is not watched.

Edit the repo copy

You change system/grub/grub. /etc/default/grub keeps the old bytes until someone copies it over.

Drift: running system does not match the repo. Silent.

Fix: apply, then rebuild grub/mkinitcpio for the boot ones. Status shows out of sync.

Edit the live /etc copy

You tweak /etc/default/grub in place and do not push the change back into the repo.

Drift: two sources of truth. Apply overwrites the live file with the repo and saves the old one under /var/lib/dotfiles/backup. Your tweak is gone from /etc.

Fix: either commit the tweak into system/ first, or accept the repo wins. This is the sharpest edge in the system.

Package update leaves a .pacnew

pacman updates a file we also own (PAM is the usual one) and drops /etc/pam.d/login.pacnew. The live file may be the new package version, the old ours, or a merge.

Drift: unknown until you look. Upstream change is not in the repo.

Fix: merge by hand into system/pam/login, then apply. Status lists .pacnew; apply does not merge for you.

Boot rebuild fails

A grub or mkinitcpio change does not build. The previous working file is rolled back; the bad hash is remembered so it is not retried until the repo file changes.

Drift: repo and live disagree on purpose. Safe, but the repo is wrong until you fix it.

Fix: fix system/mkinitcpio / system/grub/grub, change the file, apply again.

What a daily timer would actually buy. Only the copy layer: it would notice a stale /etc/default/grub and install the repo over it. Stow and system links are already live for content the moment you edit the repo; a timer only picks up new files and replaced links earlier than you would. It would also be the thing that overwrites a live /etc tweak while you are away.

What puts it back

dotfiles status

Read-only. Compares repo lists to the live tree: stow dry-run, link targets, copy cmp, .pacnew. Answers “would apply change anything?”

Does not: fix, merge, or upgrade packages.

dotfiles apply

Stow, relink, install copies, rebuild boot when a copy changed, enable the user units that ship with packages.

Does not: upgrade packages, merge .pacnew, or undo an orphan symlink you deleted from the repo.

you + paru

Package upgrades, orphans, cache. Manifests stay a shopping list for bootstrap only (bare necessities), not a drift police.

Does not: touch the three config layers.

Reading the edge. The one real footgun is the copy layer: apply always prefers the repo, so a live /etc edit is never safe unless you also write it back to system/. Everything else is either already live (symlinks) or missing until you run apply (new files).
